## Overview

Rice Monitor is a cross-platform monitoring and control application developed as
part of the undergraduate thesis **“Water Management in Rice Fields Using LoRa
Technology”** at the Federal University of Santa Catarina (UFSC), Brazil.

The project addresses a practical challenge in irrigated rice farming: obtaining
reliable, centralized and remote information about field conditions while reducing
the need for manual inspections. The solution combines environmental sensing,
long-range LoRa communication, cloud synchronization and a responsive user
interface for mobile and desktop environments.

The application displays field devices on an interactive map, presents their
current readings in real time, records recent changes and allows an operator to
send commands to irrigation gates. It was designed as the software layer of an
IoT prototype for precision agriculture.

> **Project status:** academic prototype and proof of concept. The Flutter
> application is available in this repository; the ESP32/LoRa firmware and
> physical gate assembly are described in the thesis but are not included here.

## Why it matters

Irrigated rice production depends on careful water management. Inadequate water
levels, dry soil, abnormal flow or unsuitable water quality can increase waste,
operational costs and crop risk. Rice Monitor provides a single operational view
of these conditions and supports faster, evidence-based decisions in the field.

## Features

### Authentication

- Email and password registration.
- Login validation and session navigation flow.
- Remember-email convenience option.
- Password recovery email lookup flow for the prototype.

### Live field map

- Georeferenced markers for monitoring points.
- Real-time synchronization with Firebase Realtime Database.
- Marker details for:
  - soil humidity;
  - available water level;
  - water flow;
  - water pH;
  - irrigation gate state.
- Add, reposition and remove monitoring points.
- Satellite, hybrid and standard map views.
- Responsive layouts for mobile and desktop screens.

### Operational dashboard

- Consolidated status indicators for all monitoring points.
- Counts for available water, humid/dry soil, open gates and critical points.
- Average pH overview.
- Search by monitoring-point ID.
- Filters for open gates, humid soil, dry soil, critical pH and low water.
- Sorting by ID, soil condition and pH.
- Recent history for each monitoring point.

### Alerts and remote control

- Visual identification of critical conditions.
- Recent-event notification panel.
- Remote open/close gate commands through the shared cloud state.
- Automatic map centering and marker status updates.

## Architecture

The complete prototype is organized into three cooperating layers:

```text
┌────────────────────┐       ┌────────────────────────┐
│ Remote field nodes │       │ Central node           │
│ ESP32 + sensors    │◄─LoRa─►│ ESP32 + LoRa + Wi-Fi  │
│ Gate actuator      │       └───────────┬────────────┘
└────────────────────┘                   │
                                         │
                                         ▼
                              ┌──────────────────────┐
                              │ Firebase Realtime DB │
                              └───────────┬──────────┘
                                          │ real-time sync
                                          ▼
                              ┌──────────────────────┐
                              │ Flutter application  │
                              │ Mobile / Web / Desktop│
                              └──────────────────────┘
```

### Field and communication layer

The thesis prototype uses ESP32 microcontrollers and EBYTE E32-900T30D LoRa
transceivers. Remote nodes collect sensor readings and listen for gate commands.
The central node receives LoRa packets, forwards data to Firebase over Wi-Fi and
checks for commands generated by the application.

The measured prototype inputs include:

- soil humidity;
- water level;
- water flow;
- water pH;
- gate position and state.

### Cloud layer

Firebase Realtime Database is used as the shared, hierarchical data store between
the central node and the Flutter application. Database listeners update the
interface whenever a value changes, without requiring manual refreshes.

### Application layer

The Flutter application provides the authentication flow, map visualization,
operational dashboard, history and gate-control interface. On the web, it uses
`flutter_map`; on native platforms, it uses Google Maps.

## Data model

The application expects a Firebase Realtime Database with the following
high-level structure:

```text
/
├── markers/
│   └── <marker-id>/
│       ├── latitude
│       ├── longitude
│       ├── humidity
│       ├── waterlevel
│       ├── waterFlow
│       ├── ph
│       ├── isGateOpen
│       └── history/
│           └── <entry-id>/
│               ├── timestamp
│               ├── humidity
│               ├── waterlevel
│               ├── waterFlow
│               ├── ph
│               └── isGateOpen
└── users/
    └── <user-id>/
        ├── email
        └── password
```

The dashboard stores a new history entry when a monitoring point changes and
retains the five most recent entries for each point.

## Getting started

### Prerequisites

- Flutter SDK compatible with Dart `^3.8.1`.
- A configured Firebase project with Realtime Database enabled.
- Platform tooling for the target platform:
  - Android Studio and an Android SDK for Android;
  - Xcode for iOS/macOS;
  - a supported browser for Web;
  - Visual Studio with C++ desktop tooling for Windows;
  - the corresponding Linux desktop dependencies for Linux.

### Installation

```bash
git clone https://github.com/matamboni/rice_monitor.git
cd rice_monitor
flutter pub get
flutter analyze
flutter test
```

### Firebase configuration

1. Create a Firebase project.
2. Register each target platform in Firebase.
3. Generate or update `lib/firebase_options.dart` using the FlutterFire
   configuration workflow.
4. Enable Firebase Realtime Database.
5. Add the expected `markers` and `users` nodes.
6. Configure map credentials according to the target platform:
   - Google Maps API configuration for native mobile builds;
   - web map configuration for browser builds.

Run the application with:

```bash
flutter run
```

For a specific target:

```bash
flutter run -d chrome
flutter run -d windows
flutter run -d android
```

### Important security note

This repository contains an academic prototype configuration. Before any
production deployment:

- replace the open rules in `database_rules.json` with authenticated,
  least-privilege Firebase Security Rules;
- migrate credentials to Firebase Authentication;
- never store plaintext passwords in Realtime Database;
- restrict map API keys by application, API and environment;
- validate sensor payloads and gate commands on the server side.

Do not expose a production Firebase project using the current prototype rules.

## Results from the thesis prototype

The integrated prototype was evaluated through laboratory, controlled and field
tests. The main reported results were:

- LoRa communication tested from 100 m to 6 km.
- Stable data decoding at 6 km, with a reported 25% packet-loss rate at the
  maximum tested distance.
- Average application synchronization time of approximately **1.2 seconds**.
- Water-flow measurement error of approximately **+2.7%** on the reference test.
- pH measurement of **6.56 ± 0.02**, compared with a reference value of
  approximately 6.6.
- Clear discrimination between dry and saturated soil conditions.

These results support the technical feasibility of the proposed architecture for
slow-changing agricultural variables and remote irrigation supervision. They do
not represent a production SLA or a full-season agricultural validation.

## Limitations and future work

The thesis identifies the following next steps:

- long-term, full-season field validation;
- IP67/IP68 enclosures and sensor protection;
- improved sensor self-cleaning and maintenance strategy;
- scalable network management, potentially through LoRaWAN;
- configurable rule-based automatic irrigation;
- stronger authentication and authorization;
- standardized mechanical integration with existing irrigation pipes;
- validation of solar charging and long-term energy autonomy.
